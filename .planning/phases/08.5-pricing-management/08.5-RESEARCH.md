# Phase 8.5: Pricing Management - Research

**Researched:** 2026-07-07
**Domain:** Internal CRUD rework (Drizzle/Postgres schema + Next.js admin UI) on an established stack — no new external technology
**Confidence:** HIGH

## Summary

This phase reworks the existing Phase 3 pricing admin (`/admin/pricing`) rather than building anything greenfield. The current implementation (`hostingPackages` + `domainPrices` tables, `src/lib/pricing.ts` read layer, `PricingPackagesTable.tsx` / `DomainPricesTable.tsx`) uses a per-field auto-save pattern (`onBlur` → individual PATCH → "Saved ✓" indicator). PRICE-06..10 requires: (1) create routes for packages/TLDs/add-ons, (2) a full rework of the edit UX to an explicit read-only-card → Edit → single Save-Changes → back-to-card flow, (3) an `is_active` soft-delete flag on packages and domain prices, and (4) a brand-new `addons` table + admin CRUD + public display section.

Everything needed already exists in the codebase as a pattern to mirror: `ClientForm.tsx` demonstrates the exact create-vs-edit dual-mode form shape (`clientId?` prop, POST when absent / PUT when present, `useToast()` + `Spinner`), `billing-schedules/route.ts` demonstrates the POST-with-FK-existence-check-returning-422 pattern, and `AddScheduleForm.tsx`/`StatusSelect.tsx`/`TicketStatusSelect.tsx` demonstrate the required `scheme-dark` dark-native `<select>` styling. No new npm packages, no new external service, no Context7 lookups were needed — this is 100% established-stack CRUD.

The one real design decision is the Edit→Save-card component architecture (isEditing state per card, snapshot-on-cancel) and how the PATCH routes change shape (per-field partial body today → still partial-body-capable, but the UI now sends all editable fields in one request instead of one per blur). A second real decision is where `is_active` filtering happens: **`src/lib/pricing.ts`'s public read functions must filter to active-only**, while admin routes must continue reading everything (active + inactive, so the owner can reactivate). A related, not-strictly-required consistency gap was found: `src/app/admin/automations/page.tsx` queries `hostingPackages` directly (bypassing `pricing.ts`) to populate the "Add Billing Schedule" package dropdown — this should also filter to `is_active` for consistency, but it is NOT one of PRICE-06..10's acceptance criteria, so it's flagged as an open question / stretch item, not a required task.

**Primary recommendation:** Extend the existing tables additively (migration `0009`: `is_active boolean not null default true` on both `hosting_packages` and `domain_prices`, plus a new `addons` table styled exactly like `hosting_packages`), filter `is_active` only in the public-facing `pricing.ts` reads, and rebuild the two existing admin tables (+ one new one) around a shared `isEditing` card pattern mirroring `ClientForm.tsx`'s create/edit duality and `useToast`/`Spinner` conventions already used elsewhere in `/admin`.

### Pattern 1: Edit -> Save-Changes card (PRICE-07/09/10's core UX)
**What:** Each row/card starts in a read-only display state. An "Edit" button flips a local `isEditing` boolean, revealing editable inputs pre-filled from props. A single "Save Changes" button PATCHes the entire object in one request; "Cancel" discards local edits by resetting state from props (no request). On success, `isEditing` returns to `false` and `router.refresh()` re-fetches server data.

**When to use:** All three pricing tables (packages, domains, add-ons).

**Example (structure to build, based on `ClientForm.tsx`'s dual-mode + `PricingPackagesTable.tsx`'s existing field set):**
```tsx
"use client";
import { useState } from "react";
import { useRouter } from "next/navigation";
import { useToast } from "@/components/ui/Toast";
import { Spinner } from "@/components/ui/Spinner";
import type { HostingPackageDTO } from "@/lib/pricing";

function toEditable(pkg: HostingPackageDTO) {
  return {
    name: pkg.name,
    priceRands: String(pkg.priceRands),
    pricePeriod: pkg.pricePeriod,
    description: pkg.description,
    features: pkg.features.join("\n"),
    isPopular: pkg.isPopular,
  };
}

function PackageCard({ pkg }: { pkg: HostingPackageDTO }) {
  const router = useRouter();
  const toast = useToast();
  const [isEditing, setIsEditing] = useState(false);
  const [fields, setFields] = useState(toEditable(pkg));
  const [saving, setSaving] = useState(false);

  function startEdit() {
    setFields(toEditable(pkg)); // fresh snapshot in case props changed since last edit
    setIsEditing(true);
  }
  function cancel() {
    setFields(toEditable(pkg));
    setIsEditing(false);
  }
  async function save() {
    setSaving(true);
    const res = await fetch(`/api/admin/pricing/packages/${pkg.id}`, {
      method: "PATCH",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        name: fields.name,
        priceRands: Number(fields.priceRands),
        pricePeriod: fields.pricePeriod,
        description: fields.description,
        features: fields.features,
        isPopular: fields.isPopular,
      }),
    });
    setSaving(false);
    if (res.ok) {
      toast.success("Package saved.");
      setIsEditing(false);
      router.refresh();
    } else {
      toast.error("Save failed — check the fields and try again.");
    }
  }
  async function toggleActive() {
    const res = await fetch(`/api/admin/pricing/packages/${pkg.id}`, {
      method: "PATCH",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ isActive: !pkg.isActive }),
    });
    if (res.ok) { toast.success(pkg.isActive ? "Deactivated." : "Reactivated."); router.refresh(); }
    else toast.error("Action failed.");
  }

  return isEditing ? (
    <div className="rounded-xl border border-(--border-color) bg-(--bg-primary)/80 p-5 space-y-4">
      {/* editable inputs bound to `fields`, no onBlur PATCH */}
      <div className="flex gap-2 pt-2">
        <button onClick={save} disabled={saving} className="btn-metallic px-4 py-2 text-sm disabled:opacity-60">
          {saving ? <span className="inline-flex items-center gap-2"><Spinner /> Saving…</span> : "Save Changes"}
        </button>
        <button onClick={cancel} disabled={saving} className="btn-glass px-4 py-2 text-sm">Cancel</button>
      </div>
    </div>
  ) : (
    <div className={`rounded-xl border p-5 ${pkg.isActive ? "border-(--border-color)" : "border-(--border-color) opacity-50"}`}>
      {/* read-only display of pkg fields */}
      <div className="flex gap-2 pt-3">
        <button onClick={startEdit} className="btn-glass px-4 py-1.5 text-sm">Edit</button>
        <button onClick={toggleActive} className="px-4 py-1.5 text-sm rounded-lg border border-(--border-color)">
          {pkg.isActive ? "Deactivate" : "Reactivate"}
        </button>
      </div>
    </div>
  );
}
```
This eliminates `SaveIndicator`/`saveStates`/per-field `onBlur` entirely — replaced by one `saving` boolean and one `isEditing` boolean per card.

### Pattern 2: Create route with FK/uniqueness pre-check -> 422
**What:** POST routes validate with zod, then do a plain `db.select` existence/uniqueness check before insert, returning `422 { fields: {...} }` instead of letting a raw constraint violation 500.
**When to use:** `packages` POST (slug uniqueness), `domains` POST (tld PK collision), `addons` POST (no uniqueness constraint needed, but keep the same zod-> insert shape for consistency).
**Example (from `billing-schedules/route.ts`, apply the same shape to packages):**
```typescript
// Source: src/app/api/admin/billing-schedules/route.ts (existing pattern)
const CreateSchema = z.object({
  name: z.string().min(1).max(64),
  slug: z.string().min(1).max(32).regex(/^[a-z0-9-]+$/, "lowercase letters, numbers, hyphens only"),
  priceRands: z.number().int().positive(),
  pricePeriod: z.enum(["mo", "yr"]).default("mo"),
  description: z.string().optional().default(""),
  features: z.string().optional().default(""),
  isPopular: z.boolean().optional().default(false),
});

export async function POST(req: NextRequest) {
  const session = await requireAdmin();
  if (!session) return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
  const parsed = CreateSchema.safeParse(await req.json().catch(() => null));
  if (!parsed.success) {
    return NextResponse.json({ error: "Validation failed.", fields: parsed.error.flatten().fieldErrors }, { status: 422 });
  }
  const [existing] = await db.select({ id: hostingPackages.id }).from(hostingPackages).where(eq(hostingPackages.slug, parsed.data.slug));
  if (existing) {
    return NextResponse.json({ error: "Validation failed.", fields: { slug: ["Slug already in use"] } }, { status: 422 });
  }
  const maxSort = await db.select({ max: sql<number>`coalesce(max(${hostingPackages.sortOrder}), 0)` }).from(hostingPackages);
  const [created] = await db.insert(hostingPackages).values({ ...parsed.data, sortOrder: (maxSort[0]?.max ?? 0) + 1, isActive: true }).returning();
  return NextResponse.json({ package: created }, { status: 201 });
}
```

### Pattern 3: Public read filters is_active, admin read does not
**What:** `src/lib/pricing.ts` functions used by public pages must add `.where(eq(hostingPackages.isActive, true))`. The admin page (`src/app/admin/pricing/page.tsx`) must NOT use those same filtered functions — it needs to see and toggle inactive rows too.
**Recommendation:** Rather than branch `getHostingPackages()` on a parameter, add a second explicit function so call sites are unambiguous by name (mirrors the existing 1-function-per-purpose style in `pricing.ts`):
```typescript
// Source: src/lib/pricing.ts pattern extended
export async function getHostingPackages(): Promise<HostingPackageDTO[]> {
  // PUBLIC — active only
  const rows = await db.select().from(hostingPackages)
    .where(eq(hostingPackages.isActive, true))
    .orderBy(asc(hostingPackages.sortOrder));
  return rows.map(toDTO);
}

export async function getAllHostingPackagesAdmin(): Promise<HostingPackageDTO[]> {
  // ADMIN — includes inactive, for the pricing management page
  const rows = await db.select().from(hostingPackages).orderBy(asc(hostingPackages.sortOrder));
  return rows.map(toDTO);
}
```
Same split for `getDomainPriceMap()` (public, active-only) vs. a new `getAllDomainPricesAdmin()` (admin, all rows) — note `getDomainPriceMap()`'s current `Record<tld, number|null>` return shape loses the `is_active` flag entirely, so the admin variant needs a different return shape (array of `{ tld, priceRands, isActive }` rows, not a map) to expose the toggle in the UI.

### Anti-Patterns to Avoid
- **Reusing the per-field auto-save pattern for the new tables:** PRICE-07/09/10 explicitly forbid per-field auto-save ("prevents accidental changes"). Do not copy `PricingPackagesTable.tsx`'s `onBlur`+`SaveIndicator` machinery for `addons` — it is being retired everywhere in this phase, not just where new fields are added.
- **Filtering `is_active` inside `getHostingPackages()` unconditionally without an admin variant:** would silently break the existing `/admin/pricing` page (owner could no longer see/reactivate deactivated packages) and would also silently filter the registration wizard's package picker and `register/route.ts`'s slug→name lookup down to only-active packages, which is actually correct behavior for the wizard (an inactive package shouldn't be selectable) but must be a *deliberate* choice, not an accident of one shared function.
- **Hard-deleting rows:** explicitly out of scope per the phase goal ("no hard delete"); `DELETE` routes are not needed for this phase.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Toast/success feedback | Custom inline banners per table | `useToast()` from `src/components/ui/Toast.tsx` | Already the site-wide convention (`ClientForm.tsx`, tickets, etc.); consistent a11y (`role="status"`, `aria-live`) |
| Loading spinner in Save buttons | New spinner markup | `<Spinner />` from `src/components/ui/Spinner.tsx` | Single reusable inline SVG, already used in every admin submit button |
| Slug generation for new packages | Freeform text slug input only | Derive slug from name (`name.toLowerCase().replace(/[^a-z0-9]+/g, "-")`) with the raw input still zod-validated against `^[a-z0-9-]+$` | Prevents owner typos creating slugs with spaces/punctuation that would break `?package=slug` query-param matching in `register/page.tsx`/`StepServiceSelection.tsx` |
| Dark-native `<select>` styling | Custom-built listbox for `pricePeriod` | Native `<select>` + `scheme-dark` class + `style={{ colorScheme: "dark" }}` (as in `AddScheduleForm.tsx`, `TicketForm.tsx`) | `pricePeriod` only has 2 options ("mo"/"yr") — this is NOT the flag-picker case (`CountryCodeSelect`) that genuinely needs a custom dropdown; native select is correct here and matches 3 existing precedents |
| sortOrder assignment for new rows | Manual "ask the owner for a number" input | `COALESCE(MAX(sort_order), 0) + 1` computed server-side on create | Matches how the seed data was ordered (1-6); avoids collisions/gaps the owner would have to manage by hand |

**Key insight:** Every piece of this phase already has a close analog elsewhere in `/admin` (`ClientForm`, `TicketForm`, `AddScheduleForm`, `billing-schedules` route). The main craft skill needed is disciplined copying of these patterns for three parallel entities (packages, domains, add-ons), not inventing new ones.

## Common Pitfalls

### Pitfall 1: Breaking the registration wizard / invoice defaults by filtering is_active in the wrong place
**What goes wrong:** If `getHostingPackages()` is changed to filter `is_active` and that's the ONLY change made, `/admin/pricing`'s `PricingPackagesTable` (which calls `getHostingPackages()` today) silently stops showing deactivated packages — the owner has no way to reactivate them through the UI.
**Why it happens:** `getHostingPackages()` is called from 4 different places (`src/lib/pricing.ts` itself is imported by `admin/pricing/page.tsx`, `(site)/services/page.tsx`, `(site)/register/page.tsx`, `api/register/route.ts`) with two genuinely different filtering needs (admin needs everything, public-facing needs active-only).
**How to avoid:** Add a distinct `getAllHostingPackagesAdmin()` (see Pattern 3) and repoint `admin/pricing/page.tsx` at it; leave the 3 public-facing call sites on the now-filtered `getHostingPackages()`.
**Warning signs:** After the change, deactivating a package via the admin UI and it disappearing from `/admin/pricing` itself (not just the public site) is the tell.

### Pitfall 2: `domain_prices` admin read losing the is_active flag through the existing Record<string, number|null> shape
**What goes wrong:** `getDomainPriceMap()` returns `Record<tld, number|null>` — there is nowhere in that shape to carry an `is_active` boolean. If the admin `DomainPricesTable` keeps consuming this exact function/shape, the Deactivate toggle has nothing to bind to.
**Why it happens:** The DTO shape was designed in Phase 3 before soft-delete existed.
**How to avoid:** Give the admin table a new query returning `{ tld: string; priceRands: number | null; isActive: boolean }[]` instead of reusing the map shape; keep `getDomainPriceMap()` (map shape, active-only) untouched for the public `domain-checker` page.
**Warning signs:** TypeScript will not catch this — `Record<string, number|null>` has no `isActive` key to omit-by-accident, so this is a design-time trap, not a compile-time one.

### Pitfall 3: Slug collisions / missing slug on new package creation route
**What goes wrong:** `hostingPackages.slug` has a DB-level `UNIQUE` constraint (`hosting_packages_slug_unique`). A raw insert with a duplicate slug throws a Postgres unique-violation, surfacing as an unhandled 500 (the exact failure mode the security audit already fixed once for `billing-schedules.packageId`, per SECURITY-AUDIT.md's Fixed table).
**Why it happens:** New code path, easy to skip the existence pre-check when copying the PATCH route (which never touches slug) rather than the POST-with-uniqueness-check pattern.
**How to avoid:** Pre-check slug uniqueness with a plain `db.select` before insert and return `422` (see Pattern 2's example) — mirrors the already-fixed `packageId` FK-violation precedent exactly.
**Warning signs:** A 500 response (not 422) when the owner tries to reuse an existing package name/slug.

### Pitfall 4: pricePeriod / features string handling regressions during the Edit->Save-card rework
**What goes wrong:** The current PATCH schema (`packages/[id]/route.ts`) treats every field as independently `.optional()` (correct for partial per-field PATCHes). If the new UI always sends the full object but the schema is left unchanged and a bug omits a field, the schema silently accepts the partial update instead of erroring — the row would then get a stray unintended partial-update if any client-side state bug drops a field.
**Why it happens:** The Save-Changes button is supposed to always send ALL editable fields together (single commit); an `.optional()` schema won't catch a client bug that forgets one.
**How to avoid:** Keep the PATCH schema `.optional()`-per-field to remain compatible with the pure `{ isActive: boolean }` toggle PATCH (which intentionally sends only one field), but write a component-level test/manual check confirming the "Save Changes" handler always constructs the full field set from `fields` state (not a diff) before firing — the safety net is in the UI construction, not the schema's strictness. Do not over-constrain the schema to "all-or-nothing" since the Activate/Deactivate button needs single-field PATCH capability that must coexist with the full-object Save Changes flow on the exact same route.
**Warning signs:** Editing one field and finding another field reset — indicates the UI is submitting a partial `fields` object it thinks is complete.

### Pitfall 5: New "add-ons" concept name-collides with the registration wizard's existing hardcoded add-on checkboxes
**What goes wrong:** `src/components/forms/steps/StepServiceSelection.tsx` already has a hardcoded `ADDONS` array (Domain Registration / SSL Certificate / Email Hosting / Website Design — these map to `clientRegistrations` boolean columns like `domainRegistration`, `sslCertificate`). PRICE-10's new `addons` DB table (name/description/price, shown on the public services page) is an **entirely separate, unrelated concept** that happens to share the word "add-on."
**Why it happens:** Both concepts are legitimately called "add-ons" in normal English, but one is a registration-wizard checkbox list wired to specific DB boolean columns and email-summary logic, the other is a new freeform priced-items table for public marketing display.
**How to avoid:** Do not attempt to unify them or have the wizard read from the new `addons` table — that would require redesigning `clientRegistrations`' fixed boolean columns and is explicitly out of scope. Name the new table/component distinctly in code (`addons` table is fine at the DB layer since it's a new table with no collision, but consider naming the new public-facing component `PricingAddOnsSection` or similar, and the admin table `AddonsTable`, to keep it visually distinct in the codebase from `StepServiceSelection`'s `ADDONS` constant during code review).
**Warning signs:** A future contributor searching "addons" in the codebase finding two unrelated hits and assuming they're linked.

### Pitfall 6: sortOrder omitted on addons/domains create leaving new rows unordered relative to existing ones
**What goes wrong:** `hostingPackages` and (recommended) `addons` both have a `sortOrder` column used for display order on the public site. A new package/add-on created without a sensible `sortOrder` value defaults to `0`, which would sort it FIRST (before the existing seeded rows at sortOrder 1-6), not last as the owner would expect.
**Why it happens:** The column default (`0`) exists for schema-safety, not display-order-safety.
**How to avoid:** Compute `COALESCE(MAX(sort_order), 0) + 1` server-side in the POST route (see Pattern 2) rather than relying on the column default or asking the owner to pick a number.
**Warning signs:** A newly created package/add-on visually appearing before existing ones on the public site.

### Pitfall 7: domain_prices has no sortOrder / no name column — TLD is both PK and display label
**What goes wrong:** `domainPrices.tld` is the primary key (`varchar(16)`), not an auto-increment id — the "Add TLD" create route needs to validate the TLD string itself (format, leading dot, no duplicates) rather than generating an id.
**Why it happens:** Table was designed Phase 3 with `tld` as a natural key; there is no display-order concept for domain prices (rendered as a table, likely alphabetical or insertion order) unlike packages.
**How to avoid:** POST `/api/admin/pricing/domains` schema should validate `tld: z.string().regex(/^\.[a-z0-9.]+$/)` (leading dot, lowercase) and pre-check existence via `db.select().where(eq(domainPrices.tld, tld))` before insert (PK collision would otherwise 500, same class of bug as Pitfall 3).
**Warning signs:** 500 on duplicate TLD instead of a clean 422.

## Code Examples

### Additive migration 0009 (exact DDL recommendation)
```sql
-- Source: pattern mirrors 0006_invoice_client_link.sql (single ALTER + FK, statement-breakpoint separated)
ALTER TABLE "hosting_packages" ADD COLUMN "is_active" boolean DEFAULT true NOT NULL;--> statement-breakpoint
ALTER TABLE "domain_prices" ADD COLUMN "is_active" boolean DEFAULT true NOT NULL;--> statement-breakpoint
CREATE TABLE "addons" (
	"id" serial PRIMARY KEY NOT NULL,
	"name" varchar(100) NOT NULL,
	"description" text DEFAULT '' NOT NULL,
	"price_rands" integer NOT NULL,
	"price_period" varchar(8) DEFAULT 'once' NOT NULL,
	"is_active" boolean DEFAULT true NOT NULL,
	"sort_order" integer DEFAULT 0 NOT NULL,
	"created_at" timestamp with time zone DEFAULT now() NOT NULL,
	"updated_at" timestamp with time zone DEFAULT now() NOT NULL
);
```
Notes:
- `DEFAULT true NOT NULL` on the two `ADD COLUMN` statements is critical: it back-fills all existing rows as active with a single statement (no separate `UPDATE`), and is genuinely additive/non-breaking per the project's migration convention (verified against 0006 which used the same single-statement-per-line + `--> statement-breakpoint` style, generated via `drizzle-kit generate` not hand-written, per STATE.md's 08 decision log entry: "Migration 0006 generated via drizzle-kit ... verified additive-only").
- `addons.pricePeriod` defaulting to `"once"` (not `"mo"`) reflects that add-ons are plausibly one-off setup items (SSL/design/setup fees) rather than recurring — **this should be confirmed with the owner/CONTEXT.md if one exists**, since PRICE-10's requirement text only says "name, description, price" with no period concept mentioned. If CONTEXT.md doesn't address it, the safe default is to make it a required design decision for the planner (either add `pricePeriod` matching packages' `mo`/`yr` enum, or omit period entirely and treat all add-on prices as flat one-off amounts — the codebase's `HOSTING_SETUP_FEE_NOTE` precedent in CLAUDE.md suggests flat one-off amounts are the established idiom for extra fees).
- **Generate, don't hand-write:** run `npm run db:generate` after adding `isActive`/`addons` to `schema.ts` so drizzle-kit produces migration 0009 with guaranteed constraint-naming parity, then verify the output is additive-only (no `DROP`) before committing — this exactly matches the 08-01 decision precedent.

```tsx
    <div className="mt-12 grid gap-6 sm:grid-cols-2 lg:grid-cols-3">
      {addons.map((a, i) => (
        <Reveal key={a.id} delayMs={i * 80} className="rounded-2xl border border-white/15 bg-white/8 backdrop-blur-sm p-6">
          <h3 className="text-lg font-bold text-white">{a.name}</h3>
          <p className="mt-2 text-sm text-slate-300">{a.description}</p>
          <p className="mt-4 text-2xl font-extrabold text-white">
            R{a.priceRands}{a.pricePeriod !== "once" ? `/${a.pricePeriod === "mo" ? "month" : "year"}` : ""}
          </p>
        </Reveal>
      ))}
    </div>
  </div>
</section>
```
If `addons` is empty, render nothing (same "no data, show nothing" convention the packages grid would already need — currently packages grid has no empty-state fallback on the public page, unlike the admin table which shows "No packages found").

## Open Questions

1. **Should `addons` have a `pricePeriod` concept (once/mo/yr) or are all add-ons flat one-off prices?**
   - What we know: PRICE-10's requirement text says only "name, description, price" — no period mentioned. The existing `HOSTING_SETUP_FEE_NOTE` precedent (a flat R395 once-off fee) suggests the business already has a "one-off extra fee" idiom separate from monthly hosting pricing.
   - What's unclear: Whether the owner wants recurring add-ons (e.g., "extra email account, R20/mo") as well as one-off ones (e.g., "expedited setup, R500 once").
   - Recommendation: Default schema to include `pricePeriod` (varchar(8), default `"once"`, allowing `"once"/"mo"/"yr"`) since it costs nothing extra at the schema level and is more flexible; the create/edit form can offer a period dropdown mirroring the existing `pricePeriod` select for packages. If CONTEXT.md (if one exists for this phase) already answers this, defer to it — this note is a fallback default only.

2. **Should `src/app/admin/automations/page.tsx`'s package dropdown (for new Billing Schedules) also filter to `is_active` packages?**
   - What we know: This dropdown queries `hostingPackages` directly (not through `pricing.ts`), independent of the two functions this phase changes. It is not named in PRICE-06..10's acceptance criteria.
   - What's unclear: Whether leaving deactivated packages selectable for new recurring billing schedules is an acceptable gap or an oversight the owner would want fixed in the same phase.
   - Recommendation: Treat as out-of-scope for this phase's task list unless the planner/owner explicitly pulls it in — flagging here so it isn't silently forgotten, not because it blocks PRICE-06..10.

3. **Exact wording/placement conventions for the "Add Package" / "Add TLD" / "Add Add-on" creation UI** (inline expanding form at the top of each table vs. a separate modal/page) is a UI-craft decision with no single established precedent in this codebase — `ClientForm.tsx`'s create mode is a full page (`/admin/clients/new`), not an inline table row. The planner should decide between "separate `/admin/pricing/packages/new`-style page" (consistent with clients) vs. "inline collapsible form within `/admin/pricing`" (denser, keeps all 3 pricing entities on one page as today). Given `/admin/pricing` already keeps 3 sections on a single page, an inline "+ Add Package" expandable form per section is recommended for consistency with the page's existing single-page-for-all-pricing design, but this is Claude's-discretion-level, not a blocking unknown.
